# AI 활용 기술 문서

---

## 1. 개요

본 프로젝트는 **Cursor Agent**를 개발 워크플로의 중심에 두고, 기획 문서화·구현·리팩터·티켓 관리를 AI와 사람이 나누어 진행했습니다.

**작업 순서를 규칙으로 고정**한 것입니다. 에이전트용 스킬(`/feature`, `/push`)과 룰(`.cursor/rules/`)을 이용하여, 새 대화를 시작해도 기획 → 범위 제한 구현 → 칸반 갱신의 순서를 따르게 했습니다. 문서와 코드가 어긋나는 것을 막고, 2인 작업에서 결정 사항을 사람이 기억하지 않아도 되게 하기 위한 구조입니다.


| 역할                | 담당                                             |
| ----------------- | ---------------------------------------------- |
| AI (Cursor Agent) | 기획·Task 갱신, 코드·씬 구현 초안, 문서·칸반 갱신, Godot API 조회 |
| 사람 (팀)            | 게임 방향·수치 결정, 플레이 검증, AC 확정, 완료 판정, 최종 커밋·머지 승인 |


AI 산출물은 저장소 규칙·기획서에 부합하는지 검수한 뒤 반영했으며, 재미와 밸런스적 요소는 사람이 직접 플레이하며 확정했습니다.

## 2. 사용 도구


| 도구                            | 용도                                            |
| ----------------------------- | --------------------------------------------- |
| **Cursor** (Agent / Composer) | 기능 구현, 리팩터, 문서 작성, `/feature`·`/push` 워크플로 실행 |
| **Context7 MCP**              | Godot 공식 문서 조회 (API·마이그레이션 확인)                |
| **Git / GitHub**              | `feature/`* 브랜치, main 머지, Pages 문서 배포         |
| **Godot 4.7**                 | 에디터 플레이·씬 편집 (최종 검증은 사람)                      |
| **GitHub Pages**              | 칸반 보드·기획 문서 공개, 팀 내 현황 공유                     |


Godot는 버전 간 API 변경이 잦아 모델이 기억에 의존하면 구버전 문법이 섞입니다. 엔진 관련 사항은 Context7로 공식 문서를 조회한 뒤 작성하도록 규칙에 명시했습니다.

참고: [칸반 (Notion)](https://app.notion.com/p/102c71bf78394bcaa9ff627548faf7f9?v=3c9b8c11155f8111bfeb000c00cae3b8) · [기획](https://team-sema.github.io/project-Afterburn/design/)

## 3. 개발 파이프라인

```text
[사람] 무엇을 만들지 결정하고 /feature 스킬과 함께 입력
    → [AI] 작업 준비 → 기획 작성 → 구현 → 자체 검증
    ↔ [사람] 중간 결과 확인과 수정 지시
    → [사람] 완료 판단 후 /push 입력
    → [AI] 정합성 검사 → 커밋 → main 머지 → review
    → [사람] 다른 팀원이 플레이하고 done / fix 결정
    → [AI] 결정된 상태를 저장소에 기록
```



### 단계별 역할과 자동화 범위

| 단계 | AI가 하는 일 | 사람이 하는 일 |
|---|---|---|
| 1. 기능 정의 | 관련 기획과 기존 기능을 찾아 영향 범위를 확인한다. | 기능의 목적·우선순위·플레이 방식·제약을 결정한다. |
| 2. 작업 준비 | `/feature` 입력을 받으면 최신 `main`을 확인하고 브랜치를 만든다. 작업 범위를 알리고 카드를 `doing`으로 옮긴 뒤 기획과 작업 목록을 작성한다. | `/feature`를 입력하고 AI가 제시한 작업 범위와 예상 동작을 확인한다. |
| 3. 구현 | 합의된 기획과 작업 목록에 따라 코드와 씬을 수정한다. `docs/design/`을 갱신하고 테스트와 자체 검사를 수행한다. | 중간 빌드를 플레이하고 조작감·연출·밸런스에 관해 피드백한다. |
| 4. 반영 승인 | 변경된 파일, 검사 결과와 남은 확인 사항을 정리한다. | 결과를 확인하고 저장소에 반영해도 될 때 `/push`를 입력한다. |
| 5. 저장소 통합 | `/push` 입력을 받으면 변경 내역, 기획, 작업 목록과 완료 조건을 대조한다. 검사에 통과하면 카드를 `review`로 옮기고 커밋한 뒤 `main`에 머지하고 원격 저장소에 반영한다. | 충돌이나 작업 범위 변경이 발견되면 처리 방향을 결정한다. |
| 6. 플레이 검증 | — | 다른 팀원이 빌드를 직접 플레이하고 카드를 `done` 또는 `fix`로 판정한다. |
| 7. 상태 기록 | 전달받은 판정에 맞춰 카드 위치와 이력을 갱신하고 커밋한다. | 보드의 에이전트 프롬프트를 Cursor에 전달하고 기록이 제대로 반영됐는지 확인한다. |



### 자동화하지 않은 판단

- 게임의 재미와 방향
- 난이도·수치·보상 결정
- 조작감과 화면 가독성 평가
- main 반영 승인
- 플레이 검증과 최종 `done` 판정

AI는 위 판단을 사람이 내린 뒤, 그 사이의 브랜치 생성·문서화·구현·검사·기록을 자동화합니다.

## 4. 칸반 기반 작업 관리 [칸반 (Notion)](https://app.notion.com/p/102c71bf78394bcaa9ff627548faf7f9?v=3c9b8c11155f8111bfeb000c00cae3b8)

티켓·열·태그는 **Notion 아이템 칸반**에서 사람이 관리한다. 주제별 기획서는 git `docs/design/`에 두고 의도·규칙·수치·완료 조건을 함께 관리한다. Task는 기획서 링크와 작업·검증 결과를 기록한다.

| 항목 | 역할 |
|------|------|
| Notion `이름` | 카드 제목 |
| Notion `상태` | 열 (아이디어 / 백로그 → … → 완료) |
| Notion `카드 ID` | feature slug (`player-augment-behaviors` 등) |
| `docs/design/<topic>.md` | 기능 기획서 |
| `docs/design/tasks/<slug>-tasks.md` | Task·AC |

열: 아이디어 / 백로그 → 기획 작성 중 → 구현 대기 → 구현 중 → 검증 대기 → 수정 필요 → 완료

### AI가 하는 일

- `/feature`·`/push`에서 Notion 카드 **조회만**(MCP 있을 때).
- 카드가 없으면 **제목·본문 초안만 추천** (자동 생성·열 이동 없음).
- 구현 범위·AC를 기획서·Task와 일치시킴.
- 사용자가 **「노션에 반영해줘」**라고 명시할 때만 MCP로 Notion 수정.

### 사람이 하는 일

- Notion에서 카드 **생성·열 이동·완료** (`검증 대기` → `완료`/`수정 필요`).
- 백로그 우선순위 및 열 판단.
- 2인 협업 시 같은 날 `main` pull, feature 브랜치는 짧게 유지.

`완료` 이동은 사람만 수행합니다. main 머지 후 `검증 대기`에 두고, 플레이 검증 뒤 `완료`로 옮깁니다.

### 진행 예시

1. 사람이 "통합 무기 STATUS 디테일" 개선 방향을 정리하여 AI agent에게 요청.
2. 에이전트가 `feature/weapon-status-detail` 생성, **제목·본문 초안 추천**; 사람이 Notion 카드를 `구현 중`으로 생성.
3. 기획서·Task 작성, 기획 범위 내 코드 구현, `docs/design/` 동기화.
4. `/push` — 정합성 검사 후 main 머지; 사람이 Notion에서 `검증 대기`로 이동.
5. 사람이 플레이 확인 후 `완료`(또는 `수정 필요`)로 이동.
